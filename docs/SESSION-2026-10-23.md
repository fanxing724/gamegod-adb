- 没有重签、修改或安装该原厂 APK。

### 游戏模式真实调用链

```text
PerformanceDashboardViewHolder 的模式按钮
→ IOperationService.V2(Context, boolean)
→ OperationToolService.V2
→ Settings.Secure.putInt("game_power_save_mode", enabled ? 2 : 1)
```

- `1` 对应均衡，`2` 对应游戏 / HunterBoost 开启。
- 读方法 Z5 检查同一键是否等于 2。
- 面板内部模式编号 201 / 202 与 Settings 值 1 / 2 不同，不可混用。
- 成功写入和读回只证明控制设置值，不等于 CPU/GPU 已执行对应策略。

### 其他接口线索

- `UniPerfEx.uniPerfEvent(4485, "", [0 / -1])` 存在，但未取得固件对应事件配置，不应描述成全局游戏性能开关。
- iAware 的 3006 / 3007 上报位于弹幕线程相关代码，不等于整个游戏的调度策略。
- APK 包含 PowerKit / PowerGenie 客户端、资源请求和帧率相关接口。服务端调用者验证和实际可用性未完整核验。
- `HwPowerManager.setHwBrightnessData("BrightnessSliderPresence", ...)` 是亮度滑块逻辑。
- `AudioTrack.Builder.setPerformanceMode` 是音频模式。
- 网络库 `setPerformancePreferences` 是 socket API。以上不能当成 CPU 性能调度证据。

### 签名与组件边界

原管家多个 exported 组件仍受 signature / signatureOrSystem 权限保护。没有荣耀签名私钥，不能正常覆盖安装并继承特权。ADB/Shizuku 不等于系统签名。

实机原包版本为 `18.0.21.319`，被 Hail 设置为 disabled-user（enabled=3）。本次没有解冻、删除、替换该系统包。在这种状态下，自有 App 仍能读写游戏模式值，但不能据此认定底层调度已经生效。

## 5. 新版 0.2.0 悬浮工具面板

从“点击入口返回主界面”升级为“点击入口在游戏上方展开工具面板”。

面板包含：

- 系统可用内存 / 总内存。
- 网络类型、互联网验证状态、全设备上下行计数差分。
- 电量和电池温度。
- 可读的 CPU 当前频率范围。
- CPU 总体占用候选采集路径。
- 游戏图层实际呈现 FPS 候选采集路径。
- 直接切换游戏模式，恢复会话，打开系统清理和系统电池页。

### 采集实现

- 内存用 ActivityManager.MemoryInfo。
- 网络用 ConnectivityManager 与 TrafficStats，不上传网络数据，无 INTERNET 权限，不做外部探测。
- 电池用系统电池广播，不冒充 CPU 温度。
- CPU 用 App UID 执行 `dumpsys cpuinfo`；Android 15 的 CpuBinder 调用 `checkDumpAndUsageStatsPermission`，所以 DUMP 之外还需使用情况权限 / AppOp。
- FPS 用目标游戏 SurfaceFlinger 图层的 `--latency` 实际呈现时间戳。首行是显示周期，不用于冒充 FPS。忽略未来、过期、重复、0 与 Long.MAX_VALUE 时间戳。
- 单后台线程；面板展开与折叠采用不同采样频率；诊断命令超时与输出大小有界；停止会话即停止监测。
- 不在 UI 线程执行系统诊断，不持有唤醒锁。

### 真机已观察到的新版数据

悬浮面板已经显示系统可用/总内存、移动网络及已验证状态、上下行 KB/s、电量、电池温度和 CPU 频率范围。

最初 CPU 占用显示不可用。进一步查 Android 15 官方源码，确认还需要使用情况权限；已补充 Manifest、授权说明、使用情况设置入口与代码路径，**补充后尚未完成真机读数复核**。

FPS 在当时没有近期前台游戏呈现数据的场景显示不可用；**没有完成“游戏前台时拿到有效 FPS”的验证**。不可把未验证的采集路径写成可用功能承诺。

### 内存清理限制

Android 14+ 普通第三方 App 的 killBackgroundProcesses 只能影响自己。没有批量停止用户应用，没有伪造释放内存数字。当前面板“清理运行内存 · 系统入口”交给荣耀系统管家实际执行，不能描述为自有无权限一键清理。

## 6. 系统电池性能模式

### 实机与静态交叉核对

本轮电池测试前：

- 系统性能模式开关开启。
- `Settings.System.SmartModeStatus=5`。
- `Settings.Global.low_power=0`。

通过系统原生开关关闭后，`SmartModeStatus` 变为 1。直接写回 5 时原生开关没有同步变化，说明不能把改设置值当成完整的原生性能模式切换。此前曾使用原生开关重新开启并核对过一次。

分析手机的 `com.hihonor.systemmanager` APK 得到：

- 原生智能模式：设置值 1，通知 PowerGenie 的 state 为 2。
- 原生性能模式：设置值 5，通知的 state 为 3。
- 切换流程还涉及原生控制逻辑，并发送 `hihonor.intent.action.POWER_MODE_CHANGED_ACTION`。
- 该广播被声明为 protected-broadcast。
- 对外 OpenInterfaceReceiver 受签名级访问权限保护，其入口只接受普通/省电值，不是第三方性能模式后门。

因此不伪装成能通过一个普通广播完整切换系统电池策略。

### 实现的可选辅助功能适配

- 用户主动开启“游戏模式同时启用系统性能模式”。
- 在系统界面授权星游的限定辅助功能。
- 接收事件限定为系统管家，查找精确 resource-id：`com.hihonor.systemmanager:id/perform_mode_switch`。
- 先保存原状态，打开原生电池页，操作这个开关。
- 同时检查原生勾选状态和系统值，再返回游戏。
- 游戏模式结束或切回均衡时尝试恢复原电池策略。
- 独立的电池恢复记录保留在本地，失败不因游戏记录清除而丢失。
- 只适配已核实的智能/性能状态；不擅自转换超级省电等其他模式。
- 18 秒有界超时；不点击通用允许/确定按钮，不使用通用手势脚本操作其他应用。

### 遇到的问题与修正

- 窗口内容事件频繁时，最初的“每次事件都取消并推迟轮询”可能导致轮询迟迟不运行。改成固定有界轮询。
- 增加 interactive windows 检索，并只选择系统管家根节点，避免悬浮窗口干扰活动根节点选择。
- 辅助服务短暂重连时，30 秒以内的用户请求可恢复轮询；陈旧请求不会无限期重放。
- 发现测试辅助脚本在 UIAutomator 返回 null root 时仍会读取上一次 XML，导致过期坐标风险。脚本已改为必须确认本次 dump 成功；记录中不把失败脚本输出当成功证据。
- 新增仅包含开关布尔状态的有界诊断日志，不输出窗口文本、游戏账号或聊天内容。

**截至用户要求停止测试，没有验证通过电池“自动开启 → 返回游戏 → 自动恢复”的完整闭环。** 自动请求曾打开原生电池页，但等待确认失败，恢复记录被保留。最新修正已构建，未完成真机复核。
